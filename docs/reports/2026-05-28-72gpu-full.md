## 0. 测试前修复动作

测试开始前发现本节点 (192.168.15.137) 因 5/27 跑高负载后 driver 内 NVLink 拓扑缓存被 chassis 端 bandwidth 查询不一致触发的 assertion 冻在降级状态（NCCL busbw 646 → 48）。

修复路径（未 reboot、未动 chassis、未动 IMEX 配置）：

1. 停 `nvidia-dcgm` / `nvidia-imex` / `nvidia-persistenced`
2. `rmmod nvidia_drm/modeset/uvm/nvidia` → `modprobe` 回来
3. 4/4 GPU 起来，但 GPU 2 的 18 条 NVLink 卡在 inActive
4. `nvidia-smi --gpu-reset -i 2`（单 GPU FLR）→ GPU 2 18×53.125 GB/s 全恢复
5. 重启 3 个服务 → 4 GPU 全 fabric Completed / CliqueId 32766
6. 验证 NCCL all_reduce 4-GPU: busbw **48 → 687 GB/s**（14× 恢复）

修复期间其他 17 节点未受任何影响。

## 4. 已知遗留事项



1. **NCCL busbw 仍距 NVLink-peak 有差距**: 8 GiB all_reduce peak 881 GB/s vs NVLink physical peak 1800 GB/s 双向 ≈ 49%。这是 NCCL 算法/通道选择问题（不是 fabric 中毒）。如需进一步压榨可调 `NCCL_ALGO=NVLS` / `NCCL_PROTO=Simple` / `NCCL_NCHANNELS_PER_PEER`。

2. **driver state 脆弱性**: 本次修复证明 driver 内 NVLink 拓扑缓存会被一次 chassis 端 bandwidth 查询不一致触发的 assertion 冻在降级状态。**长期方案需要 chassis 端解决 bandwidth 查询不一致问题**，否则下次高负载查询触发后还会复发，需要再次 driver reload + FLR 修复。
